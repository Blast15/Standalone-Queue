# v1.2.0-SNAPSHOT — phase 3 migration and verification

Scope: SQ-010/011/013/015, roadmap PR-08/09/10. This candidate builds on phase 2 merged at `bc72811e4c385fee78a7664baacd076f74be5143`. G3 remains pending real Paper/client/provider/network measurements and operator acceptance; this is not a production release.

## Anti-bot behavior

| Decision | Meaning |
|---|---|
| `RATE_LIMITED_UUID` | UUID retry inside `queue.rate-limit-seconds` cooldown |
| `RATE_LIMITED_IP` | IP sliding-window quota or 4096-IP tracking saturation |
| `RATE_LIMITED_GLOBAL` | Ordinary or protected global sliding-window budget exhausted |
| `QUEUE_IP_QUOTA` | New queued entry would exceed the per-IP queue quota |
| `QUEUE_FULL` | New queued entry would exceed the configured queue size |
| `RATE_LIMITED` | Lifecycle guard: duplicate/closed/registry saturation/repeated reload race |
| `PAUSED` | Queue admission intentionally paused |

The ordering is UUID cooldown, IP attempts, ordinary/protected global attempts, then queue admission/quota. UUID/IP rejections do not consume global timestamps. Queue quota/full rejection does consume the accepted anti-bot attempt. Rejected UUID retries do not slide the UUID cooldown, and cleanup preserves cooldowns longer than one minute. The 4096-entry UUID LRU may evict an unexpired identity under a sufficiently large identity flood; this is bounded traffic budgeting, not an authentication guarantee.

A live lease owner matching both original UUID and IP uses a separate global budget of the same configured size. Ordinary bot bursts cannot exhaust this protected budget. Owners still obey UUID/IP limits; a different IP gets no protected headroom. The protected budget is itself bounded, not unlimited. Phase 2 admission rechecks the lease/deadline/capacity after permissions resolve. Offline UUID/IP equality cannot authenticate an account, especially behind shared NAT; trusted online authentication/forwarding is still required for identity guarantees. IP changes may redeem a lease through the ordinary budget, never through protected headroom.

Both IP and global attempt settings now have a hard ceiling of 4096: strict reload rejects larger values, legacy startup clamps them. There are at most 4096 UUID entries and 4096 IP buckets, at most 4096 ordinary plus 4096 protected timestamps, and therefore at most 8192 accepted timestamps across IP queues. Cleanup and reload clear expired/current histories respectively. Queue storage remains bounded by `max-queue-size`; the existing O(n) per-IP queue scan is retained and measured rather than replaced with another mutable index.

Defaults remain window 10 s, UUID cooldown 2 s, IP 20 attempts/window, global 100 attempts/window, queue IP quota 5. **These defaults intentionally do not accommodate 50 queued users behind one NAT.** The controlled NAT regression uses IP 60, global 150, quota 60: 200 attempts from one bot IP accept 60 and reject 140 by IP; all 50 other-IP NAT users can queue. This establishes one scenario, not a universal safe threshold. Tune from rejection deltas and labeled legitimate staging clients, then have operations approve thresholds.

## Successful admission history and ETA

Total successful JOIN counts all exact-token/Player-identity transitions to JOINED once. Pre-login grants, failed/cancelled logins, duplicate JOIN callbacks and quit events never count as success. Rolling 5/15-minute history and ETA specifically count **successful JOINs after queued/reserved admission**; direct/bypass/disabled observer traffic cannot falsely advertise queue drain speed.

History uses 900 fixed second buckets; rolling counts have one-second resolution. Inter-arrival EWMA weights new observations by 0.25. ETA uses the slower of the EWMA interval and `300 / successfulQueuedJoins5m`, and is withheld with fewer than three recent successes, a last success 120 s old, zero usable interval, or pause. History is cached for one second; the first eligible request after a JOIN may still see the previous cache until that second expires.

Work ahead equals one-based queue rank (which already includes queued lease holders) plus redeemed-but-unfinished queued admissions. Output is an explicitly approximate 0.5×–1.5× interval range in seconds. Failed admissions no longer add work. This is a heuristic range, **not a statistical confidence interval or an entry deadline**; priority arrivals, lease expiry and player departure rates can change it. Low/no data displays `Đang cập nhật`, even at rank 1. The old `position*20s` guess is removed. A ready slot retains the ready message.

## Commands, permissions and pause policy

| Commands | Permission |
|---|---|
| `status`, `stats` | `queue.stats` |
| `inspect <player|uuid>`, `list` | `queue.inspect` |
| `pause`, `resume`, `move <player> <absolute-position>`, `clear`, `kick` | `queue.manage` |
| `reload`, `antibot` | `queue.admin` |

`queue.admin` remains a backward-compatible umbrella. All nodes default to OP. Help/tab completion only show authorized commands. The plugin.yml blanket command permission has been removed so granular grants can reach the dispatcher. Existing administrators keep access.

Pause rejects new pre-login admission/queue entry and stops new lease allocation, including bypass while queuing is enabled. Existing waiting heartbeats can renew, pre-issued live leases can redeem, and accepted handshakes can finish. Expiry and capacity reconciliation continue, so shrinking capacity may still revoke leases. Resume immediately reconciles and allocates. Pause persists across reload, resets on plugin restart, and does not change Paper admission when `queue.enabled=false` (observer mode).

Move uses an absolute one-based position, within the same priority tier only, and rejects any affected interval containing a live or unreconciled lease/connection. It preserves heartbeat/priority and does not admit anyone. Invalid arguments do not mutate state. Later arrivals remain behind current same-tier peers. Clear/kick retain their explicitly destructive queue/lease semantics.

Inspect gives UUID, tier, current rank, heartbeat TTL, lease ID/remaining TTL and connection phase without IP. Queue rank/TTL are zero for an in-flight/retained connection, with the priority frozen at admission. State may change after the snapshot. Names in presentation templates are escaped. Audit lines for pause/resume/move/clear/kick/anti-bot/successful reload remain visible with debug off and sanitize line breaks.

## Metrics and verification

`getStatistics()` provides an immutable bounded snapshot. `getMetricsText()` renders Prometheus text **after** snapshot locks release, with a fixed decision-reason label set and no UUID, name or IP labels. It reports decisions, successful joins, login failures, cancelled pre-logins, timeouts, queue/lease/in-flight/capacity/pause gauges, queued JOIN windows and pre-login average/max ms. Decision timing includes permission wait and lock contention. Counters are lifetime-of-plugin-instance; concurrent counter increments can be sampled between updates. Average/max do not claim production latency percentiles.

No HTTP exporter/listening socket is introduced. Consumers can use the Java API; any future transport must be disabled by default and bound to localhost or authenticated. Failed authentication/ban/whitelist reasons belong to their owning plugin; `failedLogins` is the final denial of a queue-owned token, not a classification of other plugins' policies.

See [G3 staging/load runbook](../testing/phase-3-staging.md) and [local benchmark](../testing/phase-3-benchmark.md). Local verification: 131 unit/regression tests plus 14 Paper API integration tests, 145 total, zero failures/errors/skips; main and staging-probe JAR builds pass. Maven tests use actual Paper API event objects with controlled player/provider doubles, not an actual server/event bus. The separate staging probe still builds against version 1.2.0 and must be removed after testing.

Upgrade: back up JAR/config, review any IP/global limit over 4096, install the candidate on staging, retain existing config (new `messages.kick-paused` has a fallback), and assign granular permissions if desired. Rollback: stop the server, restore phase 2 JAR/config and restart. Queue, counters, ETA and pause are memory-only; no phase 4 persistence is included.
