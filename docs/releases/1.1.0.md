## Login lifecycle

Each accepted pre-login receives a random `AttemptId`, UUID, IP, admission timestamp and frozen deadline. `queue.in-flight-timeout-seconds` defaults to **30**, valid reload range **5–300**. An old token cannot release a newer attempt. The internal integration method `releaseInFlight` now requires both UUID and exact token; UUID-only release is removed.

| Event/state | Capacity accounting |
|---|---|
| Accepted pre-login | One in-flight slot. |
| Deadline reached before login | Mark `TIMED_OUT`, retain slot; the old handshake may still reach login. |
| Login before deadline | Bind the exact Bukkit `Player` identity; override only `KICK_FULL`. |
| Login after deadline | Reject with `kick-login-timeout`; final rejection frees capacity. |
| Final login rejection | `FAILED`, no in-flight slot; keep connection ownership until close. |
| Accepted login, delayed join | Keep slot even after deadline; record timeout once for diagnostics. |
| Join | Capture main-thread online count and transfer in-flight to online accounting atomically. |
| Quit, then close | Quit releases online capacity. Close removes the attempt ownership record. |
| Network close before login/join | Release the pending attempt. |
| Another plugin cancels accepted async pre-login | MONITOR removes that exact token; Paper does not emit close for cancelled pre-login. |

Paper's close event carries UUID/IP, not a connection ID. Therefore only one accepted connection per UUID may remain outstanding, including `JOINED`/`FAILED` records until close. Immediate reconnect before the old close is rejected; it cannot overwrite connection ownership. There is a 4096-record ceiling. Rejected duplicate pre-logins never release the accepted token. This assumes plugins respect final event results and Paper's event ordering; it is not a guarantee for plugins that force a join after rejection or mutate MONITOR results.

Queuing disabled with `queue.enabled=false` still observes accepted handshakes, deadlines and connection ownership, and retains the existing rate/anti-bot checks. This makes later enabling account for already accepted handshakes. These observation-only attempts do not obtain `KICK_FULL` override authority, even if queuing is enabled before login. Previously accepted admissions are not retroactively revoked by reducing capacity or changing timeout. A connection stuck after accepted login retains its slot until Paper closes it, rather than making the capacity counter unsafe.

## Atomic reload

`/queue reload` reads YAML off-thread and strictly validates an immutable candidate. Malformed YAML, unreadable files, wrong field types, duplicate permission nodes and invalid ranges produce a clear admin failure. The last good settings, queue priorities, lease ownership and runtime anti-bot override stay active on failure.

Provider I/O runs outside the config monitor/queue lock. Up to 32 users refresh concurrently within the candidate's total `permissions.resolve-timeout-ms` budget. Unverified, failed, timed-out or stale permission results reject the whole reload. A queue membership change, shutdown or newer reload also rejects an obsolete candidate and asks the admin to retry. Slow storage or a busy queue may therefore prevent reload from committing; it does not publish partial defaults or partial priorities.

The commit holds config then queue locks and publishes settings, every prepared queue weight, ordering and lease reconciliation together. Live leases keep their owner, ID and original deadline across priority or duration changes. Capacity shrink revokes newest leases first. Lowering queue size retains existing waiting players and blocks new entries at the new limit. A shorter heartbeat may remove already expired entries at commit. These are explicit policy transitions, not lost queue state.

A **successful** reload resets `/queue antibot on|off` to the file value and clears UUID/IP/global attempt-window history. A failed reload preserves both. Existing in-flight deadlines remain frozen; new attempts use the new timeout. Pre-login racing a reload retries permission resolution once within its original wait budget; repeated generation changes request reconnect instead of overwriting freshly reconciled weights with an old result. Provider discovery and online/offline server mode still require a restart.

Startup retains legacy fallback/clamping for old files; reload is strict. Review old invalid values before relying on reload. Missing new keys use defaults; existing customized message templates remain valid.

## Logs and messages

```yaml
queue:
  in-flight-timeout-seconds: 30
logging:
  suppress-queue-noise: false
```

Suppression is independent of `queue.debug-log`. It defaults off, and when enabled only matches known Paper network logger names, anchored disconnect formats and an exact name/IP/plain-text reason produced by this plugin in the last 5 seconds. Recent reasons are bounded at 4096. Unknown sources/formats, UUID announcements, chat, unrelated plugin logs, WARN/ERROR and throwable events/parameters always survive. Some Paper versions print different logger names or component formats; those messages intentionally remain visible until a staging trace establishes their origin. This is conservative suppression, not a promise to hide every queue line.

`debug-log=true` adds token/UUID/phase/elapsed-time traces for accepted pre-login, timeout, login, join, quit and close. `/queue status` adds active in-flight, overdue in-flight and cumulative timeout counts. These counters are diagnostics, not performance benchmarks; individual status fields can change during concurrent events.

Expired reservation holders receive `EXPIRED_AND_REQUEUED` once when they next get a waiting decision, even if cleanup processed expiry first. `kick-reservation-expired` receives the new position and the same placeholders as `kick-in-queue`: `<position>`, `<total>`, `<online>`, `<max>`, `<time_left>`, `<priority>`, `<eta>`. Legacy `<time>` remains the current configured reservation duration; it is not a historical lease-duration measurement. MiniMessage and `&`/`§` colors are covered. If a new slot is available immediately, the player is admitted without an expired/ready kick.

`kick-slot-ready` and its formatter are deprecated compatibility entries and unused by admission. New keys `kick-login-timeout`, `kick-admission-required`, `messages.admin.reloading`, `reload-failed` and `status-line-in-flight` have defaults even in old config files.

## Validation and rollback

Java 21 `mvn -B clean verify` is authoritative. Surefire runs unit/regression tests; Failsafe runs the real Paper API event/listener harness. CI also builds the separate **staging-only** probe and uploads both test reports and separate JAR artifacts. Gradle remains IDE metadata and is not a verified release path.

Local verification on 2026-10-10: Java 21 `mvn -B clean install` passed **109 unit/regression + 14 Paper API integration tests (123 total, 0 failures/errors/skips)**. The standalone staging-probe build also passed. PR CI verifies the pushed revision and publishes the reports.

See the [staging procedure and acceptance matrix](../testing/phase-2-staging.md). The API harness does not start a Minecraft server, authenticate clients or use a real LuckPerms storage backend. Real event timing, Paper transport limits, other login plugins and production load remain G2 staging gates. No release tag or production deployment is included.

For rollback: stop the server, restore the previous JAR and backed-up config, remove the staging probe, restart. Queue state is in memory and is lost on restart. Restoring phase 1 restores the 15-second in-flight accounting risk and earlier reload/log behavior; there is no persistent schema migration.
