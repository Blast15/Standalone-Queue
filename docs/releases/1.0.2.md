# v1.0.2 — phase 1 migration and staging

Status: **1.0.2-SNAPSHOT, not released**. Code and unit regressions address SQ-001, SQ-002, SQ-003, SQ-004, SQ-005, SQ-007 and part of SQ-016 from the 2026-10-10 audit. Gate G1 remains pending until Paper staging and independent review are recorded.

## Behavior changes

| Area | v1.0.2 behavior |
|---|---|
| First VIP/admin connection | Optional LuckPerms resolves authenticated UUID permissions before queue decisions. |
| No LuckPerms | OP bypass works from a main-thread operator snapshot, maximum age 2 seconds. Other provider permissions are unsupported at pre-login. |
| Revoke while offline | No local join/quit rights cache; query LuckPerms storage on the next eligible attempt. OP changes apply on the next snapshot, or fail closed once the old snapshot reaches 2 seconds. |
| Failure / slow provider | Default maximum wait 1000 ms, ordinary rights on failure; 64 outstanding storage calls maximum. |
| Offline mode | No name/offline-UUID elevation, including OP. Existing cached bypass is no longer trusted. |
| Reserved slot | Higher-priority newcomers cannot take a live lease. Newest leases are revoked first if physical capacity shrinks. |
| Lease/heartbeat deadline | Expired at the exact deadline, processed before reconnect can renew the old turn. Expired lease holders move behind same-tier peers. |
| `/queue list` | Unmodifiable list of detached snapshots; readers cannot change manager-owned state. |

New optional config:

```yaml
permissions:
  resolve-timeout-ms: 1000
```

The setting is clamped to 1–5000 ms. Old config files work with the default. In online mode, install LuckPerms 5.4+ for non-OP VIP/bypass rights, configure queue permissions with global/static server contexts, then restart. Provider detection occurs at startup. LuckPerms API is `provided`/`compileOnly`, so it is not bundled into the plugin JAR. Do not assume dynamic world permissions or arbitrary Bukkit permission attachments are available before login. An explicit LuckPerms bypass denial wins over the default OP bypass.

Maven / Java 21 is the authoritative build: `mvn -B clean verify`. Gradle metadata is retained for IDE use, not validated as a release path. The artifact is `target/StandaloneQueue-1.0.2-SNAPSHOT.jar`. No release tag is created by this work.

- Original commit `9f220edafaab135873c374beca0d0619bd677585`: `mvn -B clean verify`, 33 tests passed.
- Four targeted repros on that same commit fail for the expected assertions: VIP steals a lease; reconnect renews an expired lease before cleanup; reconnect revives an expired heartbeat; an external list caller changes manager-owned priority. The reproduction source and command are in [phase-1-baseline.md](../testing/phase-1-baseline.md).
- Candidate: Java 21 `mvn -B clean verify`, 58 tests passed (0 failures, 0 errors, 0 skipped); 25 more than the original suite. CI on the PR is the authoritative check for the pushed revision.

## Required staging before release

Use a separate Paper 1.21.4 / Java 21 server first, with capacity 1–5 and copies of production login/permission settings. Repeat on the actual production Paper version before claiming compatibility.

1. Online mode, no LuckPerms: start with an OP UUID that has never joined. Fill capacity, confirm OP bypass, revoke OP and retry after two seconds. Confirm ordinary players remain queued.
2. Online mode plus LuckPerms: provision fresh VIP/admin UUIDs, confirm weights and bypass at the first attempt, revoke while offline and reconnect; explicitly deny bypass on an OP. Repeat with slow/unavailable storage and static server-context permissions.
3. Fill capacity with normal players. Queue A/B, free a slot, then introduce a higher-priority C. A must retain the lease. Try two simultaneous reconnects of A and confirm at most one admission; then test A/B with two leases.
4. Reconnect immediately before/at/after lease and heartbeat deadlines. Verify same-tier FIFO; lower capacity from two free slots to one and confirm newest-lease revocation.
5. Try offline mode in an isolated test environment. Name reuse must not obtain pre-login priority or bypass. Validate ordinary queue behavior.
6. Verify `KICK_FULL` is overridden only for admitted in-flight UUIDs; ban/whitelist rejections must remain rejected. Repeatedly run `/queue list` during reconnect/cleanup.
7. Record login traces, candidate JAR hash, Paper/LuckPerms versions and reviewer sign-off. Compare observed latency/throughput against the original build on the same hardware. Only then promote version/tag `v1.0.2`.

## Rollback and remaining work

Stop the server, restore the previous JAR and backed-up config, and restart. Queue state is memory-only and does not survive either restart; there is no storage migration. Rolling back restores the audited v1.0.1 defects, so use the previous build only according to your operational risk decision.

SQ-006 (the existing 15-second in-flight timeout and per-attempt lifecycle), SQ-008 (atomic reload and priority reconcile), SQ-009/012 (log/message behavior) remain phase 2. Bypass may consume physical capacity and therefore revoke leases under the documented newest-first policy. Admin clear/kick explicitly cancels reservations. Full persistence, ETA and anti-bot tuning remain later phases.
